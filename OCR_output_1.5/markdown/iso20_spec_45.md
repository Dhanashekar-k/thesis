It is recommended that the public SECC keeps the keys secure under all conditions, including while they are in use. An easy way to achieve this is to utilize HSM to store and use the keys including any cryptographic operations that use those keys.

In addition, the public SECC can also utilize the HSM to perform other cryptographic functions in a secure manner (e.g. encryption/decryption, signature calculation and verification, asymmetric key-pair generation, etc.).

The public SECC can opt to use TPM to perform all (or some) of the functions mentioned above for the HSM. Refer to 7.3.6 for details of TPM.

##### 7.3.6.3 Protection of the keys in private SECC

This subclause does not cover requirements for the SECC operating in public environment. It only covers requirements for a private SECC. Since the private SECC operates in a private environment, it is not required to follow the same security requirements as an SECC operating in a public environment.

However, to improve security of the solution, private SECC is encouraged to meet the similar security standards as an SECC operating in a public environment. Refer to 7.3.6.2 for further details.

[V2G20-2357] Any private SECC that supports PnC (using contract certificate(s)) shall meet the same security standards as an SECC operating in a public environment. Refer to 7.3.6.2 for further details.

#### 7.3.7 Random number generation

Asymmetric cryptographic algorithms like ECDSA, EdDSA, etc. strongly rely on the fact that an attacker does not have information about the random once. Otherwise, signatures would leak information about the secret key. Depending on the type of defect in the random generator implementation, this may enable an attacker to derive the secret key after a certain number of signatures. In the worst case, simple reuse of the random once will enable an attacker to calculate the secret key after only two signatures. Therefore, it is vital to have a suitable random number generator (RNG), a so-called cryptographically secure RNG. In addition, for generating the initialization vector in AES-GCM, for generating a challenge for PnC and for generating a nonce for TLS session negotiation a cryptographically secure RNG is needed.

## [V2G20-835]

Whenever a V2G entity requires random numbers within this document, a state-of-the-art cryptographically secure random number generator shall be used.

NOTE 1 There could already be a suitable, cryptographically secure random number generator available in the implementation. As the actual implementation of the RNG does not affect interoperability, this document does not prescribe a specific way in order to be future-proof and to avoid duplication. Some examples of established RNG standards are NIST SP 800-90 A, German BSI AIS 20/AIS 31, etc.
