##### 7.3.7.1 Random number generator best practices

Cryptographic algorithms are highly dependent on random numbers. An implementation of the security architecture defined by this document is only as secure as the RNG implemented by the V2G entity and secure usage of the random numbers generated by that RNG.

Random number produced by a RNG should be used/processed securely.

If the V2G entity stores the random number generated by NRBG before using it, it should ensure security of that stored random number, such that no processes other than the process that actually needs to use the random number, have access to that random number. Similarly, the V2G entity should ensure that the seed (number generated by NRBG used to re-seed DRBG) is erased from memory after it has been used to re-seed the DRBG.

If the V2G entity uses a DRBG to generate the random number and the DRBG is seeded using a NRBG, the DRBG should be re-seeded/re-initialized from the NRBG at least once every 24 h or at power-up, whichever occurs earlier.

Most cryptographic RBGs are advertised as being able to produce 0,93 bits (or so) of entropy for every 1 bit generated by the RBG. In such cases a 128-bit random number generated by the RBG will have 120 bits of entropy. Requirements below take that into account when defining the minimum entropy requirements.

Higher the entropy, better the RBG is. Most applications/features/functions in this document require minimum 0,90 bits of entropy for every 1 bit generated. That means, they require 116 bits of entropy in a 128-bit random number.

If an application/feature/function in this document does not specify a minimum entropy requirement, it should be assumed to require minimum of 116 bits of entropy for any random number used by that application/feature/function.
