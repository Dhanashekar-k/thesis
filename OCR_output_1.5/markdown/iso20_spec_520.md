D1 Size of a single certificate: Because of demand R3a, certificate size is limited. According to [V2G20-1234] the size of a certificate in DER encoded form is not bigger than 1 600 Bytes. This can be reached by the issuing secondary actor if no irrelevant information is included in the certificate (e.g. no address of the issuer). Refer to ITU-T X.509 for details of DER encoding.

D2 Length of certificate chains: Because of demand R3b complete certificates inclusive their chains should be small. Demand R5, however, demands long chains since they are easier to manage. As a compromise, [V2G20-1003] defines that the path length is limited to 3 (i.e. chains with 3 certificates below the root certificate). That means that there may exist 2 "intermediate certificates" between the root certificate and the leaf certificate. This compromise is realistic, because now each group (see R1) is able to create an arbitrary number of "intermediate organizations" (see Figure E.1) and sign the "intermediate certificates" with the (top level) root private key. Each "intermediate organization" can create "company certificates" for their secondary actors which may be used by the secondary actor itself to create leaf certificates (which represent for instance contract certificates that are distributed to the customers). As an exception, length of a certificate chain can have up to four certificates when the chain contains a cross-certificate (see [V2G20-1005]). See H.1.5 for detailed description about cross-certification.

D3 Number of root certificates: All existing root certificates are stored in each EV. Because of demand R3c, a small number of root certificates is preferred. Demand R4, however, demands a large number of root certificates. As a compromise, at least two V2G root CA certificates are required.

D4 Validity of root certificates: Because of demand R1 the (static) root certificates (installed already at EV production time) need to have an almost infinite validity. Respecting the lifetime of an EV, assumed to be 35 years, and in order to avoid the necessity to create root certificates very often (manageability of certificates, see R4 and R5), the validity period of a newly created root certificate should be 40 years.

D5 Validity of OEM provisioning certificates: OEM provisioning certificates are static certificates as well. For the same reasons as discussed in D4, it is requested that new OEM provisioning certificates have a validity period of 30 years.

D6 Installation of contract certificates: As described in R1, the best solution for the OEM would be to install all certificates at EV production. Because of R6, it is not possible to use the OEM provisioning certificate directly for (contract-based) charging since this would prevent offline EVSEs. The reason is that without communication to the backend system, it is not possible to verify whether a contract exists for an EV that only transmits a static OEM provisioning certificate (installed already at EV production independent of the existence of a charge contract).

a. Therefore, contract certificates are installed into the EV and exchanged from time to time. To avoid costs for the customer, OEM, and secondary actor this happens automatically via the charge protocol. [V2G20-1265] and [V2G20-1266] request that the SECC supports the messages CertificateInstallationReq/Res. With these messages, installation of the first contract certificate resp. installation of further contract certificates becomes possible.

b. In all cases where it is not possible to perform certificate installation automatically, the effort for manual contract certificate installation should be minimized. As described in demand R2, this can be achieved by using a standardized file format when shipping a contract certificate as file to the customer.

D7 Validity of contract certificates: It is recommended not to exchange contract certificates too often in an EV in order to avoid unnecessary write cycles for the storage of the EVCC (see demand R3). For the case that the contract certificate is shipped to the customer and is installed manually in a garage (see demand R2 and decision D6b), a short lifetime could mean it is already expired by the time it is installed into the EV.
