Private keys belonging to contract certificates need to be protected (i.e. encrypted) when distributed from the SA (eMSP) to the EVCC. This subclause (and the subclauses within) describes how the contract certificate private key is encrypted and decrypted for installation in an EVCC that contains TPM 2.0. Use of TPM to protect the keys is optional. Refer to 7.3.6 (and its subclauses) for further details.

If the EVCC does not contain a TPM 2.0, 7.9.2.5.2 (and its subclauses) applies instead.

When an EVCC that contains TPM 2.0, a private key should be encrypted for a direct import into the EVCC's TPM 2.0 to exclude a situation when these critical keys are temporarily held unencrypted in the EVCC's memory and thus made vulnerable to compromise. A direct import of contract certificate private key into the EVCC's TPM guarantees the confidentiality of private key without having to trust the EVCC's software stack.

######## 7.9.2.5.3.1 TPM 2.0 protected storage hierarchy for EVCC's keys

An asymmetric contract certificate key is a protected object in TPM 2.0, which consists of a public part and a private/sensitive part that follows a pre-defined format. The public part is described in the TPM key profile (see Table 19) and contains the contract certificate public key (in its "unique" field). The encrypted sensitive part contains the contract certificate private key. In this subclause, the term "contract certificate key" and "contract key" (or, similarly, OEM provisioning key) is used interchangeably to refer to the protected object representing the asymmetric contract certificate keys (or, similarly, OEM provisioning certificate keys). When a contract certificate public or private key is considered, it is named unambiguously. Similarly, when an OEM provisioning certificate public or private key is considered, it is named unambiguously.

TPM objects belong to a hierarchy. The import operation allows a protected object not created by a TPM such as an asymmetric contract key generated by an SA/eMSP to be incorporated into a protected storage hierarchy of the TPM. The parent for the contract key in this hierarchy is referred to as a "storage key". This subclause specifies the requirements that SAs should follow in order to provide certificates and keys in a fashion such that the EVCC can securely install asymmetric contract certificate keys under the protection of the TPM 2.0. Only TPM key profiles are specific to a particular (elliptic curve) EC, e.g. secp521r1 or Curve448. The rest of the requirements in this subclause and the subclauses within is valid for any ECC algorithm supported by EVCC.

The cryptographic protections for the contract key include encryption to prevent disclosure of the confidential contents, i.e. the private key and an integrity check to allow detection of modifications to either the confidential or the non-confidential portions of the asymmetric key object. The integrity value is computed in such a way that the confidential contract certificate private key will not be decrypted if it is not properly paired with the public area including its respective public key.

[V2G20-2511] The EVCC's TPM 2.0 shall contain a storage key pair. The storage key pair in the EVCC's TPM shall use the storage key profile from Table 19 for the default ECC algorithm (see [V2G20-2674]) or a separately defined TPM key profile for an alternative ECC algorithm (see [V2G20-2319]).

As the storage public key is used in ECDHE to encrypt the contract private key, the EVCC shall possess at least two storage keys to support the configuration mechanism defined in [V2G20-2320].

NOTE 1 OEM can generate and store a storage key pair into the EVCC's TPM in a secure environment.

NOTE 2 The storage key is a restricted decryption key, i.e. this key can only be used with specific commands and on strictly formatted objects, e.g. for direct import of specifically encrypted keys into the TPM. The storage key cannot be used for general-purpose decryption. This is one of the reasons why OEM provisioning key cannot be used as a storage key.

NOTE 3 This storage key can be a primary key of the TPM, i.e. a storage root key.
